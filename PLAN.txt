PG INVENTORY MANAGEMENT SYSTEM — PROJECT PLAN & PROGRESS
==========================================================
Last updated: this session (see chat for exact date)


CONTEXT
-------
Goal: a home/PG (paying-guest accommodation) inventory management system that
lets staff scan a barcode to quickly add a single product to stock, or photo-
scan a paper bill to bulk-add everything on it at once, with a growing shared
product library (so repeat scans of the same item are instant), and a
dashboard that flags what's running low before it actually runs out —
ideally with a real usage-based estimate ("~3 days left"), not just a static
threshold.

Stack, as requested: Supabase (Postgres + Auth + Edge Functions) for the
backend, React for the web frontend, and a phone as the scanner device
(rather than a separate native app) via an installable PWA — so one codebase
serves as both the management dashboard and the scanner, opened on a phone
browser and "installed" to the home screen.

We looked at forking an existing open-source project (HomeBox, Shelf.nu) per
the original request. Verdict: their schemas are built for tracking unique
serialized ASSETS with custody/booking/kit concepts (equipment loans,
warranties), not CONSUMABLE stock with quantities that go up and down. Forking
either would mean spending most effort stripping out irrelevant SaaS/asset-
tracking machinery (Stripe billing, multi-tenant orgs, custody, bookings)
rather than adding value. Decision: build fresh, but deliberately reuse two
proven ideas from Shelf.nu — its quantity/minQuantity/unitOfMeasure/
ConsumptionLog schema shape, and its browser-based (no native app) barcode
scanning approach using a webcam + WASM barcode reader.

Product data strategy: Zomato/BigBasket/Swiggy catalogs are proprietary and
scraping them would violate their ToS — not used. Instead: Open Food Facts
(free, open-licensed, barcode-keyed) as the primary lookup, with a Gemini
vision fallback (photo -> product name/category/unit) for anything Open Food
Facts doesn't have (common for loose produce, local/unbranded goods). Every
lookup result is cached into our own product_library table, so the system's
own catalog gets better and more complete the more it's used, specifically
tailored to what this PG actually buys.

LLM provider: Google Gemini (API key supplied by the user). Calls are made
from Supabase Edge Functions, never from the browser, so the key is never
exposed in the shipped frontend bundle. A fallback chain walks down through
progressively lighter Gemini models (2.5-flash -> 2.5-flash-lite -> 2.0-flash
-> 2.0-flash-lite) if a rate limit/quota error (429 / RESOURCE_EXHAUSTED) is
hit on the current model, so a quota ceiling on one model doesn't stop the
app from working.

Where the code lives: originally built and verified (typecheck + production
build both passing) in a sandboxed environment, then transferred to this
machine at D:\pg-inventory. Node.js was not installed on this machine and was
installed via winget (Node 24.18.0 LTS) to make that possible.


SECURITY NOTE (important, read this)
-------------------------------------
The user pasted a Supabase SERVICE-ROLE key into chat. That key bypasses every
Row-Level-Security policy in this project (full read/write/delete on all
tables) and must NEVER be placed in the frontend .env (Vite bakes VITE_-
prefixed variables directly into the JS bundle — anyone opening the deployed
site in DevTools could read it out and get full admin access to the
database). It was NOT used anywhere in this codebase. The frontend .env needs
the ANON/PUBLIC key instead (Supabase Dashboard -> Settings -> API -> "anon
public"; decode the JWT and it will say "role":"anon", not "role":
"service_role"). Recommended: rotate the service-role key from that same
Settings -> API page since it was typed into a chat session, as routine
hygiene for a key that powerful.
